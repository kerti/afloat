# pgx and sqlc for typed Postgres access

`draft`

The Go backend talks to Postgres through **`jackc/pgx/v5`** (pool, no `database/sql` wrapper) with
queries generated by **`sqlc`** from hand-written SQL. No ORM.

## Why not an ORM

The Kotlin track uses Spring Data JPA because learning it is the point of that track
(`BOOTSTRAP.md` §2). The Go side has the opposite goal: it is the canonical implementation, and its
value is that the SQL is visible.

Two of Afloat's non-negotiables are SQL-shaped and get silently wrong through an ORM:

- **Tenancy** (`BOOTSTRAP.md` §4) requires `household_id` in the `WHERE` clause of every
  Household-scoped query. With written SQL that is reviewable by reading the file. With a repository
  abstraction it is a convention someone forgets.
- **Idempotent create** is `INSERT ... ON CONFLICT (id) DO NOTHING` plus a read-back. That is a
  Postgres upsert, not a `save()`, and the ORM path is where the Kotlin side has to be argued out of
  a `SELECT`-before-`INSERT` (§4's `Persistable` footgun).

## Why sqlc rather than hand-written pgx

Hand-written `pgx` means writing the SQL *and* the scan. `sqlc` reads the same schema the migrations
produce and generates typed methods from the queries, so:

- **A query that does not match the schema fails at generation**, not at runtime on a Tuesday. Given
  `V0001` is editable in place until the first real database (`BOOTSTRAP.md` §7.1), a column rename
  turning into a build error is the property worth paying for.
- **`DECIMAL(20,4)` lands as a typed decimal**, consistently, rather than per-call-site handling.
- **It is the shape Balances arrived at** (its ADR-0018), so the auth port in step 5b is mechanical.

The cost is another generator and another `git diff --exit-code` in CI. Afloat already has two
(`oapi-codegen`, the goose files), so the marginal cost is a Makefile target, not a new concept.

## Why pgx directly, not `database/sql`

`pgx`'s native interface gives real Postgres types and does not pay `database/sql`'s conversion
layer. The one thing it costs is `database/sql` compatibility for libraries that want a `*sql.DB` —
goose being the relevant one, which takes it for migrations. `pgx` ships `stdlib` for exactly this,
so the migration path opens a `database/sql` handle at boot and the application uses the pool.

## Consequences

- `backend/internal/db` holds generated code and is never hand-edited; queries live in
  `backend/queries/*.sql`; `sqlc.yaml` sits at the backend root.
- `make gen-sqlc` generates; `make check` regenerates and diffs.
- **sqlc reads `db/migrations/` directly**, the canonical Flyway-native files — not the generated
  goose ones. There is one schema source and the generator uses it.
- Queries touching Household-scoped tables must carry `household_id` in their `WHERE`. This is
  reviewable precisely because the SQL is a file someone reads.
